# Automated Detection and Classification of 3D Printing Failures Using Image Processing and Deep Learning

## Project Overview

This project aims to automatically detect and classify failures in 3D printing images using computer vision and deep learning.

The system will:

* Detect failure locations using bounding boxes.
* Classify failure types.
* Investigate the impact of image processing techniques on object detection performance.

## Midterm Progress Status

The repository contains a working proof of concept:

* A local PyTorch YOLO26-style detector is implemented and passes a forward-pass smoke test.
* GPU training, checkpointing, mixed precision, gradient clipping, and validation loss tracking are implemented.
* Baseline, CLAHE, and CLAHE+Canny image-processing variants are generated by the same reproducible pipeline.
* Evaluation reports loss, mAP50, mAP50-95, precision, recall, per-class metrics, and a background-aware confusion matrix.

An annotation-format audit found a critical dataset issue described below. Therefore, existing experiment metrics are **preliminary diagnostic results**, not final benchmark claims. The next project phase is to normalize all labels to a single bounding-box format and rerun the controlled comparisons.

Classes:

### Current Annotation-Format Limitation

The downloaded source labels contain a mixture of standard five-field YOLO bounding boxes and polygon annotations. A detection label must use exactly:

```text
class_id x_center y_center width height
```

The raw training split contains the following annotation rows:

| Row type | Spaghetti | Stringing | Warping |
| --- | ---: | ---: | ---: |
| Five-field bounding box | 3,851 | 1,026 | 334 |
| Polygon row with more than five fields | 269 | 378 | 46 |

The current detector expects bounding boxes. Because polygon rows are not yet normalized to enclosing boxes, the current experiment metrics must not be used as final performance results. Before final benchmarking, the dataset must be re-exported as bounding-box detection labels or the polygons must be converted to five-field boxes.

## Proposed Methods

### Object Detection Models

* YOLO26-style one-stage detector: implemented as the primary model.
* Faster R-CNN: planned alternative comparison architecture; not yet implemented in this repository.

## Implemented YOLO26-style Pipeline

This repository includes a local PyTorch YOLO26-style architecture based on the Figure 1 backbone-neck-head flow and official YAML-style components described in the YOLO26 paper. It is a from-scratch educational implementation, not an official Ultralytics package model.

### Components

* `models/yolo26_torch.py` defines the backbone, PAN/FPN neck, C3k2, SPPF, C2PSA attention, and dual one-to-many/one-to-one detection branches.
* `test.py` runs a forward-pass smoke test and prints output tensor shapes.
* `train_yolo26.py` trains the model from scratch using Task-Aligned Assignment, BCE classification loss, IoU box loss, AdamW, AMP, and gradient clipping.
* `eval_yolo26.py` evaluates a saved checkpoint on validation or test data.
* `detection_metrics.py` computes AP, mAP50, mAP50-95, precision, recall, per-class metrics, and a detection confusion matrix.

Run the architecture smoke test:

```bash
python test.py
```

Expected output shape pattern:

* one_to_many: `(batch, 4 + num_classes, 8400)`
* one_to_one: `(batch, 300, 6)`

### Image Processing Techniques

The preprocessing pipeline compares three domain-engineered input variants:

* **Baseline:** RGB input.
* **CLAHE:** RGB -> LAB conversion -> CLAHE on the L channel -> RGB.
* **CLAHE+Canny:** RGB -> LAB -> CLAHE -> Canny edges blended into the enhanced image.

The script also selects interpolation based on resize direction: area interpolation for downscaling and cubic interpolation for upscaling.

Optional train-only minority-class augmentation supports horizontal flip, brightness, contrast, gamma, Gaussian noise, slight blur, translation, and scale. It clears prior generated split files and uses parameter signatures plus image hashes to avoid exact duplicate samples. Because source labels currently mix boxes and polygons, augmentation results should be treated as exploratory until label normalization is complete.

## Evaluation Metrics

* mAP50
* mAP50-95
* Precision
* Recall
* IoU
* Per-class AP50, AP50-95, precision, and recall
* Detection confusion matrix with a background row/column for unmatched GT boxes and false-positive detections

The evaluator performs decoded one-to-one-head inference over the selected split, then calculates dataset-level metrics after processing all images. mAP and confusion-matrix results currently remain preliminary because of the source-label limitation.

## Getting Started: Image Processing Pipeline

This project compares three preprocessing tracks before object detection:

* Baseline: RGB input only.
* Method 1: RGB -> LAB -> CLAHE.
* Method 2: RGB -> LAB -> CLAHE -> Canny edge enhancement.

### 1. Install Dependencies

```bash
pip install -r requirements.txt
```

### 2. Build Preprocessed Dataset Variants

Run from the project root after obtaining normalized five-field detection labels:

```bash
python preprocess_dataset.py --input-dir roboflow-data --output-dir processed-data
```

This generates:

* `processed-data/baseline/`
* `processed-data/clahe/`
* `processed-data/clahe_canny/`

Each variant includes:

* `train/images`, `train/labels`
* `valid/images`, `valid/labels`
* `test/images`, `test/labels`
* `data.yaml`

Each preprocessing run deletes and regenerates the relevant output split, preventing stale augmented files from carrying into a later experiment.

Optional minority-class augmentation is train-only:

```bash
python preprocess_dataset.py --input-dir roboflow-data --output-dir processed-data --augment-minority-train --minority-target-ratio 0.5
```

Use augmentation only after normalizing polygon labels to boxes. A ratio of `0.5` is a conservative starting point; it should be compared against a clean no-augmentation baseline.

### 3. Train and Compare Models

Use each variant's `data.yaml` for YOLO and Faster R-CNN experiments. Compare:

* mAP50
* mAP50-95
* Precision
* Recall
* IoU

The YOLO26-style model trains from scratch and the evaluator reports loss plus decoded detection metrics. Checkpoints are currently selected by validation loss, while mAP is reported separately during evaluation. Final report-quality benchmarking requires clean normalized labels and rerun experiments.

GPU training example:

```bash
python train_yolo26.py --data-root processed-data/baseline --device cuda --epochs 40 --batch-size 8 --imgsz 640 --workers 0 --save-dir runs/yolo26/baseline
```

Suggested rerun with lower learning rate (5e-5):

```bash
python train_yolo26.py --data-root processed-data/baseline --device cuda --epochs 20 --batch-size 8 --imgsz 640 --workers 0 --lr 5e-5 --save-dir runs/yolo26/baseline_e2e_lr5e-5
```

Quick GPU sanity run:

```bash
python train_yolo26.py --data-root processed-data/baseline --device cuda --epochs 1 --batch-size 4 --imgsz 320 --fraction 0.05 --workers 0 --save-dir runs/yolo26/debug
```

Validation evaluation:

```bash
python eval_yolo26.py --checkpoint runs/yolo26/baseline/best.pt --data-root processed-data/baseline --split valid --device cuda --batch-size 8 --imgsz 640 --workers 0
```

Validation evaluation for the 5e-5 run:

```bash
python eval_yolo26.py --checkpoint runs/yolo26/baseline_e2e_lr5e-5/best.pt --data-root processed-data/baseline --split valid --device cuda --batch-size 8 --imgsz 640 --workers 0
```

Test evaluation:

```bash
python eval_yolo26.py --checkpoint runs/yolo26/baseline/best.pt --data-root processed-data/baseline --split test --device cuda --batch-size 8 --imgsz 640 --workers 0
```

Test evaluation for the 5e-5 run:

```bash
python eval_yolo26.py --checkpoint runs/yolo26/baseline_e2e_lr5e-5/best.pt --data-root processed-data/baseline --split test --device cuda --batch-size 8 --imgsz 640 --workers 0
```

### Notes

* Labels are currently copied unchanged from the original Roboflow export. The known mixed box/polygon labels must be normalized before final training and evaluation.
* Canny settings are configurable in the script CLI.
* The CLAHE + Canny method overlays edges on the CLAHE-enhanced image to keep visual context while emphasizing defect boundaries.
* Existing saved checkpoints and metric outputs are retained as preliminary evidence of a functioning pipeline, not as final accuracy claims.
