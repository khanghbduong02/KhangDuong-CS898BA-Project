# Automated Detection and Classification of 3D Printing Failures Using Image Processing and Deep Learning

## Project Overview

This project aims to automatically detect and classify failures in 3D printing images using computer vision and deep learning.

The system will:

* Detect failure locations using bounding boxes.
* Classify failure types.
* Investigate the impact of image processing techniques on object detection performance.

## Midterm Progress Status

The repository contains a working proof of concept:

* A local PyTorch YOLO26-style detector is implemented and passes a forward-pass smoke test.
* GPU training, checkpointing, mixed precision, gradient clipping, and validation loss tracking are implemented.
* Baseline, CLAHE, and CLAHE+Canny image-processing variants are generated by the same reproducible pipeline.
* Evaluation reports loss, mAP50, mAP50-95, precision, recall, per-class metrics, and a background-aware confusion matrix.

An annotation-format audit found a critical dataset issue described below. The preprocessing pipeline now normalizes raw polygon annotations to enclosing YOLO bounding boxes. A later exact-image audit also found duplicate content and annotation disagreements across the exported splits. All currently reported split metrics are therefore **preliminary diagnostic results**, not leakage-free generalization estimates. The audit, controlled experiments, and required group-disjoint cross-validation protocol are recorded in [PROJECT_WORK_LOG.md](PROJECT_WORK_LOG.md).

### Current Annotation-Format Limitation

The downloaded source labels contain a mixture of standard five-field YOLO bounding boxes and polygon annotations. A detection label must use exactly:

```text
class_id x_center y_center width height
```

The raw training split contains the following annotation rows:

| Row type | Spaghetti | Stringing | Warping |
| --- | ---: | ---: | ---: |
| Five-field bounding box | 3,851 | 1,026 | 334 |
| Polygon row with more than five fields | 269 | 378 | 46 |

The detector expects bounding boxes. During preprocessing, five-field source rows are preserved as standard YOLO `class_id x_center y_center width height` boxes, while polygon rows are converted to their enclosing bounding boxes. This produces strict five-field labels for training and evaluation. Existing checkpoints must be regenerated because they were trained before this conversion was implemented.

## Implemented YOLO26-style Pipeline

This repository includes a local PyTorch YOLO26-style architecture based on the Figure 1 backbone-neck-head flow and official YAML-style components described in the YOLO26 paper. It is a from-scratch educational implementation, not an official Ultralytics package model.

### Components

* `models/yolo26_torch.py` defines the backbone, PAN/FPN neck, C3k2, SPPF, C2PSA attention, and dual one-to-many/one-to-one detection branches.
* `test.py` runs a forward-pass smoke test and prints output tensor shapes.
* `train_yolo26.py` trains the model from scratch using Task-Aligned Assignment, BCE classification loss, IoU box loss, AdamW, AMP, and gradient clipping.
* `eval_yolo26.py` evaluates a saved checkpoint on validation or test data.
* `detection_metrics.py` computes AP, mAP50, mAP50-95, precision, recall, per-class metrics, and a detection confusion matrix.

Run the architecture smoke test:

```bash
python test.py
```

Expected output shape pattern:

* one_to_many: `(batch, 4 + num_classes, 8400)`
* one_to_one: `(batch, 300, 6)`

### Image Processing Techniques

The preprocessing pipeline compares three domain-engineered input variants:

* **Baseline:** RGB input.
* **CLAHE:** RGB -> LAB conversion -> CLAHE on the L channel -> RGB.
* **CLAHE+Canny:** RGB -> LAB -> CLAHE -> Canny edges blended into the enhanced image.

The script also selects interpolation based on resize direction: area interpolation for downscaling and cubic interpolation for upscaling.

Optional train-only minority-class augmentation supports horizontal flip, brightness, contrast, gamma, Gaussian noise, slight blur, translation, and scale. The pipeline normalizes labels before augmentation, clears prior generated split files, and uses parameter signatures plus image hashes to avoid exact duplicate samples. Augmentation results from checkpoints created before label normalization remain exploratory and should be rerun.

## Current Status

Midterm proof-of-concept stage. The implementation and label-format normalization pipeline are complete. Clean RGB, CLAHE, and CLAHE+Canny comparisons plus several imbalance ablations have been completed, and the five-class candidate dataset has been evaluated with a source-stem/perceptual-group-disjoint three-fold CV diagnostic. The fixed custom focal-plus-weight model achieved mAP50 $0.0615 \pm 0.0064$ across those folds, but annotation adjudication, more real minority examples, and a newly reserved external group-disjoint test set are still required before final generalization claims.

A separate one-class Spaghetti architecture control was also completed using 3,000 exact-unique Platform Cam images split into three filename-provenance-proxy/exact-hash-disjoint folds. The neutral, randomly initialized YOLO26-style model reached mAP50 $0.2149 \pm 0.0309$, precision $0.5349 \pm 0.0662$, and recall $0.1851 \pm 0.0326$ at threshold `0.25`. This verifies that the local pipeline learns a repeatable detection signal on a larger one-class task, but the low recall means it is not yet a deployment-quality detector or evidence of multi-defect generalization. See [PROJECT_WORK_LOG.md](PROJECT_WORK_LOG.md) for results, limitations, and the full protocol.

A pretrained YOLO11n practical reference was evaluated on the identical frozen control folds using the same project metric implementation after Ultralytics NMS. It reached mAP50 $0.4699 \pm 0.0359$ and recall $0.4929 \pm 0.0364$ at threshold `0.25`, versus custom YOLO26's mAP50 $0.2149 \pm 0.0309$ and recall $0.1851 \pm 0.0326$. Because it also differs in pretraining, model/loss implementation, augmentation, preprocessing, optimizer, and NMS, this is a practical benchmark rather than an architecture-only comparison. It demonstrates that the frozen one-class data can support materially stronger detection and identifies the custom system as the main practical bottleneck. See [PROJECT_WORK_LOG.md](PROJECT_WORK_LOG.md) for the full comparison and next protocol decision.

The same pretrained YOLO11n reference also substantially outperformed the fixed custom model on the five-class group-disjoint candidate folds: mAP50 $0.4799 \pm 0.0262$ versus $0.0615 \pm 0.0064$. It improves AP50 and recall for every class, including Warping and Stringing. The candidate data remains insufficient for final deployment claims, but it is not inherently incapable of supporting multi-class learning. A pre-registered resolution-only 960-pixel ablation was then run on those same folds with all loss, sampler, weighting, augmentation, threshold, and duration settings unchanged.

That 960-pixel custom ablation is now complete. It improved aggregate custom performance to mAP50 $0.0782 \pm 0.0161$ and mAP50-95 $0.0259 \pm 0.0065$, with all three folds improving aggregate mAP relative to the 640-pixel custom baseline. The gain is not uniform: Warping and Over Extrusion improve, while Stringing declines. Therefore 960 is retained only as an aggregate-mAP candidate configuration; no further resolution or hyperparameter sweep is planned.

The fixed class-aware NMS diagnostic is now complete and requires no retraining. Applying class-aware NMS with IoU $0.70$, candidate score $0.001$, and at most 300 detections before top-$k$ truncation raises the 960 custom result to mAP50 $0.1127 \pm 0.0232$, mAP50-95 $0.0343 \pm 0.0076$, and precision $0.1621 \pm 0.0497$, with essentially unchanged recall at $0.0588 \pm 0.0172$. This is the current custom evaluation/inference decoder; use `--postprocess legacy_topk` only to reproduce historical reports. No further export-level sweeps are planned.

### Reusable K-fold cross-validation

The project separates one-fold model logic from cross-validation orchestration:

- [train_yolo26.py](train_yolo26.py) and [eval_yolo26.py](eval_yolo26.py) train/evaluate one standard YOLO dataset root containing `data.yaml`, `train/`, and `valid/`.
- [run_yolo26_kfold_cv.py](run_yolo26_kfold_cv.py) and [eval_yolo26_kfold_cv.py](eval_yolo26_kfold_cv.py) run and aggregate any dataset arranged as `fold_1/`, `fold_2/`, and so on. They infer class metadata from each fold's `data.yaml`, validate taxonomy consistency, and run folds sequentially.
- [run_ultralytics_kfold_cv.py](run_ultralytics_kfold_cv.py) and [eval_ultralytics_kfold_cv.py](eval_ultralytics_kfold_cv.py) provide a generic pretrained Ultralytics reference workflow for the same fold layout.

Example custom YOLO26 K-fold invocation:

```bash
python run_yolo26_kfold_cv.py --data-root cv-data/my-dataset --run-root runs/yolo26/my-study --epochs 50 --lr 5e-5
python eval_yolo26_kfold_cv.py --data-root cv-data/my-dataset --run-root runs/yolo26/my-study --conf-thresh 0.25
```

Use `--dry-run` with either script to inspect detected folds and commands without starting training or evaluation.

## Getting Started: Image Processing Pipeline

This project compares three preprocessing tracks before object detection:

* Baseline: RGB input only.
* Method 1: RGB -> LAB -> CLAHE.
* Method 2: RGB -> LAB -> CLAHE -> Canny edge enhancement.

### 1. Install Dependencies

```bash
pip install -r requirements.txt
```

### 2. Build Preprocessed Dataset Variants

Run from the project root. The pipeline converts raw five-field YOLO boxes and polygon rows into strict five-field detection labels in each processed dataset variant:

```bash
python preprocess_dataset.py --input-dir roboflow-data --output-dir processed-data
```

This generates:

* `processed-data/baseline/`
* `processed-data/clahe/`
* `processed-data/clahe_canny/`

Each variant includes:

* `train/images`, `train/labels`
* `valid/images`, `valid/labels`
* `test/images`, `test/labels`
* `data.yaml`

Each preprocessing run deletes and regenerates the relevant output split, preventing stale augmented files from carrying into a later experiment.

Optional minority-class augmentation is train-only:

```bash
python preprocess_dataset.py --input-dir roboflow-data --output-dir processed-data --augment-minority-train --minority-target-ratio 0.5
```

Normalization occurs automatically before augmentation. A ratio of `0.5` is a conservative starting point; it should be compared against a clean no-augmentation baseline after the clean labels are regenerated.

### 3. Train and Compare Models

Use each variant's `data.yaml` for YOLO and Faster R-CNN experiments. Compare:

* mAP50
* mAP50-95
* Precision
* Recall
* IoU

The YOLO26-style model trains from scratch and the evaluator reports loss plus decoded detection metrics. Checkpoints are currently selected by validation loss, while mAP is reported separately during evaluation. Final report-quality benchmarking requires clean normalized labels and rerun experiments.

GPU training example:

```bash
python train_yolo26.py --data-root processed-data/baseline --device cuda --epochs 40 --batch-size 8 --imgsz 640 --workers 0 --save-dir runs/yolo26/baseline
```

Suggested rerun with lower learning rate (5e-5):

```bash
python train_yolo26.py --data-root processed-data/baseline --device cuda --epochs 20 --batch-size 8 --imgsz 640 --workers 0 --lr 5e-5 --save-dir runs/yolo26/baseline_e2e_lr5e-5
```

Quick GPU sanity run:

```bash
python train_yolo26.py --data-root processed-data/baseline --device cuda --epochs 1 --batch-size 4 --imgsz 320 --fraction 0.05 --workers 0 --save-dir runs/yolo26/debug
```

Validation evaluation:

```bash
python eval_yolo26.py --checkpoint runs/yolo26/baseline/best.pt --data-root processed-data/baseline --split valid --device cuda --batch-size 8 --imgsz 640 --workers 0
```

Validation evaluation for the 5e-5 run:

```bash
python eval_yolo26.py --checkpoint runs/yolo26/baseline_e2e_lr5e-5/best.pt --data-root processed-data/baseline --split valid --device cuda --batch-size 8 --imgsz 640 --workers 0
```

Test evaluation:

```bash
python eval_yolo26.py --checkpoint runs/yolo26/baseline/best.pt --data-root processed-data/baseline --split test --device cuda --batch-size 8 --imgsz 640 --workers 0
```

Test evaluation for the 5e-5 run:

```bash
python eval_yolo26.py --checkpoint runs/yolo26/baseline_e2e_lr5e-5/best.pt --data-root processed-data/baseline --split test --device cuda --batch-size 8 --imgsz 640 --workers 0
```

### Notes

* Raw five-field labels are interpreted using the documented YOLO convention: `class_id x_center y_center width height`.
* Raw polygon rows are converted to enclosing YOLO boxes during preprocessing; training rejects any processed label row that is not exactly five fields.
* Canny settings are configurable in the script CLI.
* The CLAHE + Canny method overlays edges on the CLAHE-enhanced image to keep visual context while emphasizing defect boundaries.
* Existing saved checkpoints and metric outputs are retained as preliminary evidence of a functioning pipeline, not as final accuracy claims.
